## สิ่งที่พบและแก้จริง

1. ส่งต่อ 2 → 1 → 0 แล้วส่งคืน 0 → 1 ไม่สามารถส่งคืนต่อ 1 → 2: แก้ให้ค้นหาการส่งต่อที่ยังไม่ถูกส่งคืนใน Tier ปัจจุบัน เคสเดิมส่งคืนย้อนครบสายงานได้ และไม่คืนซ้ำ
2. หน้าส่งมอบงานเลือกรายชื่อจากทีมของผู้ส่ง: แก้ให้รายชื่อตรงเส้นทางผลิตภัณฑ์และ Tier ของทุกเคสในชุด ตรวจเงื่อนไขเดิมซ้ำที่ Backend ก่อนส่งทั้งหมด
3. โปรแกรมตรวจอัตโนมัติที่เปิดแยกจากเว็บโหลดโมเดลลูกค้า/บริบทไม่ครบ ส่งต่อ S1 แล้ว transaction ย้อนกลับ: พบจากการรอรอบจริง 5 นาที แก้การโหลดโมเดลและเพิ่ม regression ที่เปิด Python process ใหม่
4. ตรวจความพร้อมผู้รับ S1 ซ้ำภายใต้ row lock ก่อนส่งงาน หากเพิ่งไม่พร้อม ให้คงผู้รับเดิมและแจ้งปัญหาแก่ผู้ดูแล
5. หน้า Admin แสดง Tier เดิมเมื่อเลือกผู้ใช้ กรองหัวหน้าทีมให้ตรงทีม อธิบาย Role/Team/Tier และแจ้งเมื่อยังไม่มีผลิตภัณฑ์หรือยังไม่พบการทำงานของบริการตรวจอัตโนมัติ

## วิธีตรวจผ่านหน้าเว็บด้วยตนเอง

1. Admin เปิด `/routing/admin` ตรวจผลิตภัณฑ์ ทีมทั้งสาม Tier หัวหน้าทีม และ Tier ของสมาชิก หน้านี้ตั้งครั้งแรก/เมื่อทีมเปลี่ยน ไม่ต้องตั้งทุกเคส
2. เจ้าหน้าที่หน้าด่านเปิดเคส NEW ที่ยังไม่มีผู้รับ แล้วกดรับเคส หรือให้หัวหน้าทีมกดมอบหมาย
3. ในเคสกดส่งต่อ Tier เลือกผู้รับ กรอกข้อมูลสามช่องให้ครบ จากนั้นเข้าบัญชีผู้รับตรวจ Assignee ใหม่และข้อมูลส่งต่อในประวัติ Owner ต้องคงเดิม
4. ผู้เชี่ยวชาญส่งต่อให้ทีมพัฒนาได้ ผู้รับกดส่งคืนพร้อมคำแนะนำ จากนั้นผู้เชี่ยวชาญส่งคืนให้หน้าด่านต่อได้ ใช้เลขเคสเดิมตลอด
5. หน้าการส่งมอบงาน `/routing` ปิดความพร้อม เลือกผู้รับแทนพร้อมเหตุผล และส่งเคสทั้งหมด ตรวจว่าผู้รับเห็นเคส ส่วน Owner เดิมไม่เปลี่ยน
6. ทดสอบ S1/NEW ค้างด้วยเคสจำลอง และตรวจว่าบริการตรวจอัตโนมัติเปิดอยู่ รอรอบได้ถึง 5 นาที กรณี NEW ต้องอยู่ในเวลาทำการของปฏิทินที่เลือกด้วย

ใช้ข้อมูล DEMO เท่านั้นเมื่อทดลอง และตรวจสถานะปัจจุบันก่อนกด เพราะข้อมูลเดิมที่ผู้ใช้ลองไว้ไม่ได้ถูกรีเซ็ต

## วิธีทดสอบรอบอัตโนมัติ

ใช้ฐานข้อมูลเฉพาะ `isms_esc_browser_qa` บนพอร์ต 5437, API 8768, Next.js 3102 และโปรแกรม `python -m app.jobs.routing_worker` จริง เริ่มจากปิดกฎ S1 แล้วเปิดผ่านหน้า Admin ตั้ง X = 1 นาที จากนั้นรอรอบ 300 วินาทีตามโปรแกรม ไม่มีการเร่งนาฬิกาและไม่มีการเรียกฟังก์ชันส่งต่อแทนผู้ตรวจอัตโนมัติ

ข้อมูลตั้งต้นของเคสทดสอบถูกเตรียมให้อายุเกินเกณฑ์ และใช้ปฏิทินทดสอบเปิดทุกวัน เพื่อทดสอบได้ทันที ส่วนวันหยุดและเวลาเปิด–ปิดใช้การทดสอบ Backend แยก ผลจึงยืนยันพฤติกรรมระบบในเงื่อนไขที่ระบุ ไม่ใช่การอนุมัติใช้งานจริงโดยบริษัท

## เปิดใช้งานบนเครื่องนี้

เปิด Docker Desktop ก่อน แล้วเปิดโฟลเดอร์ `isms-app` ใน VS Code และใช้ Terminal ที่ราก repository:

```powershell
docker compose -f docker-compose.yml -f docker-compose.override.yml -f docker-compose.frontend.yml -f docker-compose.routing.yml up -d --wait db app frontend routing-worker
```

เว็บ `http://localhost:3100/login` → Admin ตั้งค่าที่ `/routing/admin`; ผู้ปฏิบัติงานเปิดเคสจาก My Work เพื่อส่งต่อ/ส่งคืน; การเปลี่ยนกะที่ `/routing` ไม่ต้องติดตั้ง MariaDB แยก เพราะฐานข้อมูลอยู่ใน Docker เดิม เก็บข้อมูลลง database volume เมื่อยืนยันการทำรายการ

`/preview/...` เป็นหน้าดูตัวอย่าง ใช้หน้าที่ login จริงเมื่อทดสอบการบันทึก บัญชี `demo.*` เป็นบัญชีจำลองบนเครื่อง ไม่ใช่กระบวนการสมัครบัญชีจริง การสร้างสมาชิกและทีมใช้ Users & Teams ที่มีอยู่

## ขอบเขตที่ต้องเข้าใจตรงกัน

- การแจ้งเตือนเป็นในเว็บ ไม่ส่ง LINE/email ภายนอก
- ปุ่มรับทราบ/เข้า In Progress นับการเริ่มตอบสนอง ไม่ใช่การส่งข้อความสาธารณะให้ลูกค้าในโมดูล WRK
- เวลาต่อ Tier เป็นเวลาที่เคสอยู่ใน Tier ไม่ใช่การคำนวณ SLA; ช่วงเก่าก่อนมี ESC ระบุเป็นค่าประมาณ
- Round-robin/การมอบหมายตามทักษะเป็น nice-to-have ใน SRS และไม่ใช่เกณฑ์บังคับรอบนี้
- ไม่ได้เพิ่ม Dashboard/KPI; ตรวจว่าไม่สร้างเคสใหม่ จึงไม่เพิ่มจำนวนเคสสำหรับ KPI-01 ในเฟสถัดไป
- ไม่มีการเปลี่ยน schema เพิ่มในรอบตรวจนี้ ไม่ล้างข้อมูลเดิม ไม่ merge และไม่ deploy
